# 迴圈工程規範｜Loop Engineering

## 這套方法在做什麼
以前的做法：我下一個 prompt，Claude 回一次，我看結果，我再下一個 prompt。
迴圈工程的做法：我寫一個迴圈定義，迴圈自己下 prompt、自己檢查結果、自己決定要不要再跑一輪，跑到達成停止條件才停。

我的工作從「寫提示詞」換成「設計迴圈」。

出處：Addy Osmani（2026/6）提出方法論，Peter Steinberger 把它壓成一句話——
別再 prompt 你的 agent，去設計那個 prompt 你的 agent 的迴圈。

---

## 一個迴圈的四個部位

| 部位 | 問題 | 在這個專案裡長什麼樣 |
|---|---|---|
| 觸發器 Trigger | 什麼時候開始跑 | 手動執行 `loops/run-loop.sh`，或排程 |
| 拓樸 Topology | 誰做事、誰檢查 | 生產者一個 Claude，驗證者另一個 Claude |
| 驗證器 Verifier | 怎麼算做完 | `.claude/skills/loop-verifier.md`，輸出 PASS / FAIL |
| 停止規則 Stop rules | 什麼時候放棄 | 次數上限、成本上限、無進展偵測 |

---

## 五個元件 + 一個記憶體

1. **Automations（自動化觸發）** — 排程或手動啟動，讓迴圈真的會跑，而非等我按下去
2. **Worktrees（隔離工作區）** — 不同迴圈各跑各的分支，互不覆蓋
3. **Skills（技能檔）** — 專案知識寫成檔案，每輪自動載入，省去重複交代背景
4. **Connectors（外部工具）** — MCP 連到 Notion、Gmail、Drive，讓迴圈碰得到真實資料
5. **Subagents（子代理）** — 獨立的驗證者，跟生產者分開，避免自己改自己打分
6. **State（外部記憶體）** — `loops/state/*.md`，記錄做了什麼、看到什麼、還缺什麼，讓下一輪接得上

---

## 三道護欄

迴圈跑得起來很容易，停得下來才難。沒有護欄的迴圈會一直燒 token。

| 護欄 | 設定 | 觸發後 |
|---|---|---|
| 次數上限 | `max_iterations` | 跑滿就停，寫進狀態檔 |
| 成本上限 | `max_cost_usd` | 累計花費超過就停 |
| 無進展偵測 | `no_progress_limit` | 連續 N 輪檔案沒變化就停 |

第三道最重要。卡住的 agent 會安靜地一直重跑同一個錯誤，次數和成本上限要很久才擋得住它。

---

## 生產者 / 驗證者分離

同一個模型寫完自己打分，幾乎一定給自己 PASS。所以驗證由另一次獨立呼叫執行，它只拿到產出和停止條件，拿不到生產者的推理過程。

停止條件用白話寫，而且要驗得出來：

- 可以驗：「三支腳本都通過 anti-style.md 檢查，每支開場鉤子在前 3 秒」
- 驗不出來：「內容品質良好」

---

## 什麼時候用迴圈，什麼時候不用

**適合做成迴圈**
- 會重複的產出（每週客戶週報、每月廣告成效報告）
- 有明確對錯的檢查（語氣規範、禁用詞、格式長度）
- 需要多輪修的東西（初稿 → 檢查 → 改 → 再檢查）

**不要做成迴圈**
- 一次性的判斷
- 停止條件說不清楚的任務
- 需要我拍板的決策，例如報價、要不要接案

---

## 給 Claude 的指示
使用者要我建一個迴圈時，照 `loops/` 底下既有的定義檔格式寫，
設定好三道護欄，寫出驗得出來的停止條件，然後告訴使用者怎麼執行。
